# 修正案の作り方

## 制約（仕様 D-37）

1. **最小限の修正**：警告の解消に必要な箇所だけを変える。リファクタリング、整形、無関係な改善はしない。
2. **関数の外部仕様を変えない**：引数・戻り値・公開ヘッダ・グローバル変数のインタフェースは変更しない。
3. **既存のコードスタイルに合わせる**：周囲のインデント（タブ / スペース）、命名、括弧の位置、エラー処理の書き方（`goto` による後始末、戻り値のエラーコードなど）に合わせる。
4. **社内コーディング規約に従う**：規約の資料は未共有です（仕様 U-3）。共有後にこの節へ追記します。
5. 修正によって、MISRA / CERT の別の規則に新たに違反しないようにする（例: 暗黙の型変換を増やさない、関数の出口を増やす場合は既存の書き方に従う）。

## 制約内で直せない場合（仕様 D-38）

- 制約を超えた修正案を作る（例: 関数の戻り値を変える）。
- 提出データの `fix.exceeded_constraints` に、超えた制約と理由を書く（例：「関数の外部仕様: 戻り値でエラーを返す必要がある」）。
- `fix.impact` に、影響を受ける呼び出し元をすべて挙げる。

## 手順

1. `fix` 作業領域で、修正箇所を `read_source` で読む（最新リビジョンなので、調査時と行番号がずれていることがある）。
2. `edit_source` で修正する。`old_text` は前後の行を含めて一意に一致させる。インデントの空白も正確に写す。
   - ファイルの文字コード（UTF-8 / Shift_JIS）と改行コードはツールが保持する。日本語のコメントを追加してよいが、Shift_JIS のファイルでは Shift_JIS で表せる文字だけを使う。
3. 修正後に `read_source` で読み直し、意図どおりかを確認する。
4. `save_fix`（kind=`fix`）で保存する。`message` はコミットメッセージとして使われる。形式：
   ```
   Fix Coverity CID 12345 (NULL_RETURNS)

   get_buf() の戻り値の NULL チェックを追加
   ```
5. `fix.impact` には、修正による振る舞いの変化（どの条件で何が変わるか）と、影響範囲（呼び出し元など）を書く。

## アノテーション（仕様 D-59 (b)、`deviation_target` が `coverity+annotation` の場合）

- `annotation` 作業領域で、警告行の**直前の行**にブロックコメントで入れる。理由は逸脱コメントと同じ文章にする（skill `deviation-comment`）。
- `[...]` の中は、★（main）のイベントの `tag` にする。判定によって次のように書き分ける（Coverity は `:FALSE` が無い注釈を「意図的（Intentional）」として扱うため）。

  | 判定（`verdict.judgement`） | 書き方 |
  |---|---|
  | `false_positive`（誤検知） | `/* coverity[<tag>:FALSE] 誤検知。... */` |
  | それ以外（意図的、修正しない本物のバグなど） | `/* coverity[<tag>] 意図的。... */` |

  ```c
  /* coverity[misra_c_2012_rule_10_4_violation:FALSE] 誤検知。... */
  ```
- インデントは警告行に合わせる。`save_fix`（kind=`annotation`）で保存する。
- タグ名の正確な書式は社内の Coverity バージョンで確認中です（docs/design.md 7 章）。
