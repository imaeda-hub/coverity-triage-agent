# 困ったとき

まず `ct.py doctor --repo <リポジトリ>` で状況を確かめます。

## MCP サーバが動かない

症状：`check_connection` などの MCP のツールが見つからない、MCP サーバの起動に失敗する。

1. uv が入っているか確かめる（ターミナルで `uv --version`）。無ければ `/coverity-setup` で入れる。
2. uv を入れたあと、VS Code（または Copilot CLI）を再起動したか確かめる。再起動していなければ、再起動してもらう。
3. `ct.py prewarm` を実行して、MCP サーバの Python 環境を作り直す。
4. 表示に `invalid peer certificate: UnknownIssuer` や `--system-certs` があるときは、社内のネットワークの証明書を uv が信頼していません。プラグインを最新にしてください（MCP サーバの起動とスクリプトは `--native-tls` で OS の証明書を使います）。
5. VS Code の場合は、コマンドパレットの **MCP: List Servers** で `coverity-triage` を選び、**Show Output** の内容を見る。社内のプロキシでライブラリを取れないときは、環境変数 `HTTPS_PROXY` が要るか社内の担当に確かめる。

## 実行が止まったとき

`/coverity-run` は、どれかの AI が止まっても、なるべく最後まで進めます。止まる・飛ばすのは次のときです。実行の状況は `ct.py status --run <実行フォルダ>`、初回解析の状況は `ct.py initial-status --run <実行フォルダ>` で確かめられます。

| 起きたこと | どうなるか | すること |
|---|---|---|
| 初回解析が失敗した | トリアージを始めずに止まる（古い警告を調べないため）。失敗した段（環境の設定・ビルド・解析・サーバへの登録）とログの最後がチャットに出る | 下の「初回解析」の表で原因を確かめ、設定や環境を直して `/coverity-run` で再開する（初回解析からやり直す） |
| サブエージェントが見つからない・起動できない | 取得：チャットの AI が代わりに Coverity から取って続ける。作業：その警告は「処理できなかった作業」になる。統合：まとめずに進む。検証：その作業は「未検証」で進む | `/coverity-setup` でサブエージェントの定義を置き直し、Copilot CLI を再起動する。処理できなかった作業は、`/coverity-run` の再開でやり直せる |
| 検証できなかった（「未検証」） | 検証の AI が起動できなかった、途中で止まった、検証の結果の形が直らなかった、検証の間に結果ファイルか差分が変わった、のどれか。その作業は確かめずに先へ進む。確信度は作業の AI のまま | 詳細レポートを、人がいつもより丁寧に確かめる。続けて起きるときは、上の行と同じく定義を確かめる |
| 統合できなかった（「統合はできませんでした」） | 統合の AI が起動できなかった、途中で止まった、または計画の形が直らなかった。作業はまとめずに、そのまま進む（それぞれの結果は使える） | 同じ原因の警告は、人がそれぞれ判断する。理由は実行フォルダの `operations.log` にある |
| 作業の AI の結果ファイルが、2 回直しても通らない | その警告は「処理できなかった作業」になり、次へ進む | `/coverity-run` の再開でやり直す |
| 警告経路を取れなかった（「警告経路を取れなかった警告が … 件あります」） | 取得を 2 回試しても取れなかった警告は、経路なしで調べる（確信度が下がることがある） | 続くときは、Coverity への接続と権限を確かめる |
| チャットを閉じた・PC を再起動した | 実行は途中のまま残る | `/coverity-run` で再開する（終わった警告は飛ばす。初回解析が途中で止まっていたときは、初回解析からやり直す。裏で動き続けていれば、終わるのを待つ） |

### 初回解析

| 表示・症状 | 原因と対処 |
|---|---|
| `初回解析に失敗しました（ビルド（cov-build））` | ビルドのコマンドか環境の問題。ログ（実行フォルダの `analysis/initial.log`）の最後を見る。`/coverity-setup` の「ビルドでの検証」で試しのビルドをして、設定を直す |
| `初回解析に失敗しました（解析（cov-analyze））` | `verify.cov_analyze_args` の誤り（`--dir` が `cov_build_args` と違う など）か、解析のライセンス・ディスクの空き。ログを見る |
| `初回解析に失敗しました（サーバへの登録（cov-commit-defects））` | 登録の失敗。ストリームの権限、ユーザ名・認証キー、URL を確かめる。認証キーのファイルを使うサイトは、`verify.cov_commit_args` に `--auth-key-file <ファイル>` などを書く |
| `… 分たっても終わらなかったため止めました` | `verify.timeout_minutes` を超えた。ビルドが入力待ちで止まっていないか確かめる。ふだんから時間がかかるなら、値を大きくする |
| `初回解析の設定（ビルドのコマンド）がありません` | `verify.initial` が true なのに、`verify.build_command` が空。`/coverity-setup` の「ビルドでの検証」で設定する。その実行だけ使わないなら `/coverity-run 解析はしないで` |
| `サーバへの登録に使う認証情報がありません` | 環境変数 `COV_USER` / `COV_AUTH_KEY` が無い。`/coverity-setup` の認証情報の手順で入れる |
| `初回解析のプロセスが途中で止まりました` | PC の再起動などで、裏で動いていた解析が止まった。`/coverity-run` で再開する（初回解析からやり直す） |
| `ct.py doctor` で「初回解析の cov-build」などが ng | Coverity の解析のツールが PATH に無い。Coverity の `bin` フォルダを PATH に足す（社内の手順で）。環境設定のコマンドで足しているなら warning になり、そのままでかまわない |

## 画面（監視・結果・設定）

| 症状 | 原因と対処 |
|---|---|
| 画面が開かない（ブラウザが出てこない） | `ct.py gui` の結果の `browser_opened` が false。結果の `url` を伝えて、ブラウザに貼り付けて開いてもらう |
| `画面を起動できませんでした` | 結果の `log_tail` に理由がある（使えるポートが無い、など）。もう一度 `ct.py gui` を試し、だめなら `log_tail` を添えてプラグインの管理者に連絡する |
| 画面に「この画面は … アドレスで開いてください」と出る、操作が `forbidden` になる | アドレスの確認用の文字列（`?t=...`）が無いか古い（画面のサーバが起動し直した など）。`ct.py gui --repo <リポジトリ>` で開き直し、新しいタブを使う（古いタブは閉じる） |
| ページを表示できない（接続が拒否された） | 画面のサーバが止まっている（「サーバを止める」を押した、PC を再起動した、別の画面のサーバに置き換わった など）。`ct.py gui --repo <リポジトリ>` で起動し直す。社内のプロキシの設定で `127.0.0.1` に届かないときは、ブラウザのプロキシの例外に `127.0.0.1` と `localhost` を足す |
| 画面を止めたい | 右上のメニューの「サーバを止める」を押す（確認が出る）。結果のファイルや設定は消えない |
| 画面を開き直したい | 同じアドレスを開くか、`ct.py gui --repo <リポジトリ>`（実行を見るときは `--run <実行フォルダ>`、結果を見るときは `--view summary` も）。動いていれば同じ画面を使い回す |
| 監視の画面が動かない（数字が変わらない） | タブが隠れている間は新しくしない。タブを前に出す。それでも変わらなければ、画面のサーバが止まっていないか確かめる（上の行） |
| 監視に「⚠ 停止?」が出る | その警告に 10 分のあいだ動きが無い（初回解析の枠は 30 分。ビルドが長く黙っていることもあるので、`analysis/initial.log` が増えているかも見る）。調べるのに時間がかかっているだけのこともある。チャットでサブエージェントがまだ動いているか確かめる。止まっているなら、チャットの AI がそのエージェントの `task` を `ct.py tick --failed <task> --reason "..."` で知らせ（警告は「処理できなかった」として記録される）、あとで `/coverity-run` の再開でやり直せる。何度も出るときは、`parallel` を減らすか、件数を減らして実行する |
| 監視の枠に「調査中」しか出ない（コードを読む・真偽を判断 などが出ない） | サブエージェントが進み具合のファイルを書いていない。調査には影響しない（記録だけで表示している）。サブエージェントの定義が古いと書かないことがあるので、`/coverity-setup` で最新にする |
| 監視に実行が出ない | 実行フォルダが設定の出力先（`output_dir`）の下に無い、または設定ファイルが読めない。`ct.py doctor` で確かめる |
| 結果で承認を変えると `... はまだ終わっていません` | その警告はまだ調べ終わっていない。`/coverity-run` が終わってから選ぶ |
| 結果で承認を変えると `統合・検証が終わって一覧ができてから承認できます` | 統合・検証（オプション）を使う実行では、一覧ができるまで承認を選べない（統合と検証で結果が変わることがあるため）。`/coverity-run` が終わるのを待つ |
| 結果で `逸脱の内容に直すところがあります` | 逸脱の Classification / Action / Severity / コメントのどれかが空か、Classification などに改行がある。表示された項目を直して保存する |
| 結果で反映済みの注意が出る | もう反映した警告の承認を変えた。変えても、反映した内容（Coverity の分類、push したブランチ）は元に戻らない |
| 古い実行（0.3 までで作った実行）で、詳細レポートが画面に出ない | 古い実行には HTML のレポートが無い。`cid/<ID>.md` を開くか、その実行で `ct.py summary --run <実行フォルダ>` をもう一度実行する（HTML のレポートを作り、承認を `approvals.json` に移す。画面の「結果」で承認を 1 つ保存したときも、同じように作って移す） |

## エラーの表示と対処

| 表示・症状 | 原因と対処 |
|---|---|
| `設定ファイルがありません` | リポジトリの一番上のフォルダを開いていないか、まだ準備していない。`/coverity-setup` |
| `条件ファイルが見つかりません` | 名前の誤り。結果の `filters` に、あるファイルの名前が出る |
| `設定の値が正しくありません` / `YAML の書式が正しくありません` | 設定ファイルの書き間違い。表示された項目を [settings.md](settings.md) と照らして直す |
| `条件にはストリームを 1 つだけ指定してください` | 条件ファイルの `streams` が 0 個か 2 個以上。1 つにする |
| `出力先がリポジトリの中です` | `output_dir` をリポジトリの外にする |
| `ユーザ名または認証キーが設定されていません` | `/coverity-setup` の認証情報の手順で入れる |
| `認証に失敗しました（HTTP 401）` | ユーザ名か認証キーの誤り、または認証キーの期限切れ。作り直して入れ直す |
| `10 秒以内に応答がありません` / `Coverity に接続できません` | URL の誤りか、社内のネットワークに入っていない |
| `CERTIFICATE_VERIFY_FAILED` など証明書のエラー | 社内の CA 証明書が OS に入っていない。`coverity.ca_file` に CA 証明書のファイルを指定する |
| `Coverity の列に ... が見つかりません` | Coverity の列の名前が想定と違う。`/coverity-selftest` の ③ を実行し、結果をプラグインの管理者に共有する |
| `Coverity REST ... が失敗しました` / `Coverity SOAP ... が失敗しました` | 表示されたメッセージで判断する（ストリーム名の誤り、権限が足りないなど） |
| サブエージェント `coverity-triage-worker` を起動できない | 定義が `%USERPROFILE%\.copilot\agents` に無いか古い。`/coverity-setup` を実行し、VS Code（Copilot CLI）を再起動する |
| サブエージェント `coverity-triage-collector`・`coverity-triage-integrator`・`coverity-triage-reviewer` が見つからない | 定義が `%USERPROFILE%\.copilot\agents`（環境変数 `COPILOT_HOME` があれば、その中の `agents`）に無いか古い。プラグインを更新したあとに `/coverity-setup` をしていないと起きる。`/coverity-setup` を実行し、Copilot CLI を再起動する（止まったときの扱いは上の「実行が止まったとき」） |
| `ct.py doctor` に「古いサブエージェント」が出る | プラグインに無くなった古い定義が残っている。`ct.py install-agent`（`/coverity-setup`）で消し、Copilot CLI を再起動する |
| サブエージェントがモデルを使えないと言って止まる | GPT-6 Luna を使えるか、Copilot の契約・組織の設定を確かめる |
| 修正用のフォルダの読み書きの確認が何度も出る | 確認の画面で「このセッションでは許可」を選ぶ。Copilot CLI では `/add-dir <フォルダ>` でも許可できる |
| `承認欄に直すところがあります` | 古い実行（`approvals.json` が無い）の `summary.md` の承認欄に、「修正」「逸脱」「却下」以外が書かれている。`problems` の行を直すか、画面の「結果」で選び直す |
| `逸脱の節の目印 ... が見つかりません` | 古い実行の `cid/<ID>.md` の目印の行を消した。[usage.md](usage.md) の形に戻すか、画面の「結果」で逸脱の内容を保存し直す |
| `確認用の文字列が反映の内容と一致しません` | 確認のあとで内容が変わった（画面で承認を変えた など）。もう一度 `/coverity-apply` |
| `一覧がありません（/coverity-run の最後に ct.py summary で作ります）` | その実行はまだ終わっていない。`/coverity-run` で再開して最後まで進める |
| `push できませんでした` | git の認証、またはリモートの権限。いつも使っている方法で `git push` できるか確かめる |
| `svn patch で競合しました` | 修正を作ったあとで同じ箇所が変わった。差分ファイル（`patches/`）を見て手で直す |
| 一覧に「処理できなかった作業」がある | 理由が表にある。直して `/coverity-run` で再開すると、その分だけやり直す |
| 一覧に「未処理の作業」がある | 途中で止まった。`/coverity-run` で再開する |
| レポートに「パスを自動で対応づけました」「対応づけられませんでした」 | Coverity のパスとリポジトリのパスが違う。`coverity.path_strip_prefixes` を設定する |
| ビルドでの検証が「当てられない」 | 同じ実行の別の修正案と同じ箇所を変えているため、まとめて確かめられなかった。差分を見て判断する |
| ビルドでの検証が「確かめられない」 | 別の修正案のビルドエラーで確かめられなかった |
| とても遅い | 件数を減らして実行する。Coverity の応答が遅いときは、実行フォルダの `issues.json` の `requests`（問い合わせごとの秒数）を管理者に共有する |

実行中のエラーは、画面の「監視」の「重大なエラー」にも出ます（選ぶと詳しい内容が開きます）。
解決しないときは、その表示と、実行フォルダの `operations.log`（認証情報は伏せてある）を添えて、プラグインの管理者に連絡します。
