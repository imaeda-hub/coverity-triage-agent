# 警告の真偽の調べ方

## 基本の考え方

- Coverity のイベント（警告経路）は「こう実行されたら問題になる」という**仮説**です。仮説の各段階がコード上で本当に成立するかを、1 つずつ確かめます。
- 判断の根拠は、すべて**コード上の場所（ファイル・行）**で示せるようにします。「たぶん」「通常は」で判断しません。
- 調査は `analyzed`（Coverity が解析したリビジョン）で行います。修正は `fix`（最新リビジョン）で行うため、両者の差にも注意します。

## 手順

1. **イベントを順に読む**：`get_issue_detail` の `events` を順に、`read_source` で該当行の前後（目安 ±20 行）を読む。★（main）のイベントが問題の発生箇所。
2. **経路の成立条件を洗い出す**：その経路を通るために必要な条件（分岐の条件、引数の値、戻り値など）を列挙する。
3. **条件を 1 つずつ検証する**：
   - 値の出どころを `search_source` で呼び出し元・定義元までたどる（関数名、マクロ名、変数名で検索）。
   - 呼び出し元がすべて条件を満たさない（例: すべての呼び出し元で NULL チェック済み）なら、その経路は成立しない。
   - 1 つでも条件を満たす呼び出し元があれば、経路は成立し得る。
4. **判定する**（`verdict.judgement`）
   - `true_bug`：経路が成立し、実際に問題が起きる。
   - `false_positive`：経路が成立しない（Coverity が見落とした条件がある）。
   - `intentional`：経路は成立するが、設計上意図した動作で問題にならない（例: 意図的なフォールスルー、意図的な無限ループ）。
   - `undetermined`：実行時の値や外部仕様に依存し、コードから決められない。
5. **最新リビジョンを確認する**：`fix` で同じ箇所を読み、既に直っていないかを確認する（直っていれば `fix.already_fixed_on_latest`）。

## グループの場合

- まず代表の CID を上記の手順で調べ、残りの CID が**同じ理由**で同じ結論になるかを確認する。
- 理由が違う CID は `group_excluded_cids` に入れて、個別処理に戻す。迷う場合も外す（誤ってまとめるより安全）。

## 手元のコードで調査する場合（ずれの確認）

`prepare_workspaces` が `drift_check` を返した場合、解析時のコードと手元のコードが違う可能性があります。

- イベントの行に、イベントの説明と合うコードがあるかを確認する。
- 合わない場合は `revision_drift.status` を `detected` にし、何がずれているかを `detail` に書く。確信度は下げる。
- 確認できたら `none`、確認しきれなければ `unknown` にする。

## 確信度の基準（仕様 D-64）

| 確信度 | 基準 |
|---|---|
| `high`（高） | 警告経路をコード上で最後まで追え、根拠がすべてコードにある |
| `medium`（中） | 根拠の一部に推定を含む（例: 呼び出し元の一部が追いきれない、マクロの展開結果を推定した） |
| `low`（低） | 実行時の値や外部仕様など、コードから判断できない前提に依存する。またはリビジョンのずれが検出された |

`confidence_reason` には、上の基準のどれに当たるかを具体的に書きます（例：「全 3 箇所の呼び出し元で NULL チェックを確認した」）。

自動検証（ビルド・再解析）は、全件の調査後にまとめて行われます。そこで問題（ビルド失敗、警告が残る、新しい警告）が出た修正案は、ツールが確信度を自動で「低」に下げます（仕様 D-74）。

## 推奨案の決め方（仕様 D-48）

当面はあなたの判断に任せます。目安は次のとおりです。

- `true_bug` → 修正を推奨する。
- `false_positive` / `intentional` → 逸脱を推奨する。ただし、修正が小さく安全で、コードの意図も明確になる場合は修正を推奨してもよい。
- `undetermined` → 修正のリスクが小さければ修正、大きければ逸脱を推奨し、確信度は `low` にする。
