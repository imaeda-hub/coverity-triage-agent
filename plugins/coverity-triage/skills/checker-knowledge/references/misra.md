# MISRA C / C++ の判断観点（初版）

運用で得た知見を追記していく資料です。

## 考え方

- MISRA の違反は「動作上のバグ」ではなく「規約違反」であることが多い。判定は次のように考える。
  - コードが本当に規則に違反している → `true_bug`（規約違反として）。修正するか、逸脱として正当化するかを検討する。
  - 規則の対象外（Coverity の解釈違い、生成コード、例外条項に該当）→ `false_positive`。
  - 違反しているが、設計上必要で安全性が説明できる → `intentional`（逸脱）。
- 規則の分類で扱いが変わる。**Mandatory** は逸脱できないため、修正を推奨する。**Required** は正式な逸脱の手続きが必要、**Advisory** は比較的柔軟。
- 1 つのマクロや型定義が原因で大量に出る違反は、グループ化されていることが多い。原因の 1 箇所を直す修正案が最も効果的。

## よく出る規則

- **Rule 10.x（基本型モデル）**：暗黙の型変換。修正は明示的なキャストや型の統一。値の範囲で安全性を説明できれば逸脱も可。
- **Rule 11.x（ポインタ変換）**：ハードウェアレジスタへのアクセスなど、組込みで必要な変換は逸脱になりやすい。
- **Rule 15.5（関数の出口は 1 つ）**（Advisory）：既存コードの書き方に合わせ、逸脱になりやすい。
- **Rule 21.x（標準ライブラリ）**：使用禁止の関数。代替関数への置き換えが修正案になる。
- **Directive 4.x**：Coverity が近似的に判定するため、誤検知の可能性を丁寧に確認する。
