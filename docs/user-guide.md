# 利用手順書（日々使う人向け）

Coverity の警告のトリアージを AI に任せるための手順書です。プラグインの仕組みを知らなくても使えるように書いています。
チームの設定（`.coverity-triage/`）は、設定担当者が [導入手順書](setup-guide.md) で用意済みであることが前提です。

## このエージェントがすること・しないこと

| する | しない（人がする） |
|---|---|
| 条件に合う警告を Coverity から取り出し、ソースコードを調べて本物のバグか誤検知かを判断する | どちらの案を採用するかの決定 |
| **すべての警告について「修正案」と「逸脱コメント案」の両方**を作り、推奨案と確信度を付ける | 承認していない内容の反映 |
| 一覧サマリと、警告ごとの詳細レポートを作る | svn のコミット（反映後に人が行う） |
| 人が承認した分だけ、Coverity への登録・プルリクエスト作成・svn への差分の適用を行う | |

あなたのワーキングコピーは、承認して反映するまで一切変更されません。

---

## 1. 最初に 1 回だけ（パソコンの準備）

所要時間の目安：30 分

### 1.1 必要なソフトを入れる

| ソフト | 確認方法（コマンドプロンプトで実行） | 入っていない場合 |
|---|---|---|
| VS Code と GitHub Copilot 拡張機能 | VS Code の Copilot Chat が開ける | 社内の手順で導入 |
| GitHub Copilot CLI（ターミナルで使う場合のみ） | `copilot --version` | 社内の手順で導入 |
| uv（プラグインが内部で Python を使うための道具） | `uv --version` | PowerShell で `powershell -c "irm https://astral.sh/uv/install.ps1 \| iex"` を実行し、ターミナルを開き直す |
| git または svn | `git --version` / `svn --version` | 社内の手順で導入 |

- Python を別に入れる必要はありません（uv が自動で用意します）。
- 社内プロキシの環境では、uv がパッケージを取得できるよう環境変数 `HTTPS_PROXY` の設定が必要な場合があります。

### 1.2 プラグインをインストールする【試用後に確定】

社内のプラグイン配布元（社内 GitHub のマーケットプレイス）から `coverity-triage` をインストールします。

- VS Code：拡張機能のビューで、エージェントプラグインの一覧から `coverity-triage` をインストール
- Copilot CLI：プラグインのインストールコマンドで `coverity-triage` を指定

正確な操作は試用後にここへ記載します。

### 1.3 インストールできたか確認する

VS Code の Copilot Chat で、エージェントの一覧に `coverity-triage` が表示されれば成功です。初回は、プラグインの準備（Python のパッケージ取得）に 1〜2 分かかることがあります。

### 1.4 環境変数を設定する

パスワードやトークンを設定ファイルに書かないため、自分の PC の環境変数に設定します。コマンドプロンプトで次を実行してください（`setx` で設定した値は、**新しく開いたターミナルと、再起動した VS Code から**有効になります）。

```bat
setx COV_USER あなたの Coverity ユーザ名
setx COV_AUTH_KEY あなたの Coverity 認証キー
setx GITHUB_TOKEN あなたの GitHub トークン
```

- `COV_AUTH_KEY` の入手方法は導入手順書の 2 章（No.4）を見てください。
- `GITHUB_TOKEN` は git のリポジトリでプルリクエストを作る場合だけ必要です（svn の場合は不要）。
- 設定担当者が別の環境変数名を指定している場合は、その名前で設定してください。

## 2. トリアージを実行する

1. VS Code で**対象リポジトリのフォルダ**を開く（`.coverity-triage` フォルダがあるフォルダ）。
2. Copilot Chat を開き、次のように入力する。

```
/coverity-run untriaged-high.yaml
```

- `untriaged-high.yaml` の部分は、使いたい条件ファイルの名前です（`.coverity-triage/filters/` にあるもの）。
- 条件を追加したい場合は、続けて書けます。例：`/coverity-run untriaged-high.yaml Impact は High だけにして`
- 自動検証をしたい場合も書けます。例：`/coverity-run untriaged-high.yaml ビルドで検証して`
- Copilot CLI の場合も同じコマンドを入力します。

3. 実行が始まると、AI が次を報告します。
   - 見つかった件数と、処理する件数（上限を超えた分は今回は処理しません）
   - 「手元のコードで調査します」と出た場合は、Coverity が解析した時点のコードではなく、今のコードで調べることを意味します（ずれがあればレポートに書かれます）。

4. 終わると、**一覧サマリの場所**が表示されます。

```
<出力先>/<実行日時>/summary.md
```

- 時間の目安：1 件あたり数分（警告の内容と自動検証の有無によります）。
- 途中で止まった・止めた場合は、[6 章](#6-中断した実行を再開する) で続きから再開できます。

---

## 3. 結果を確認する

### 3.1 一覧サマリ（summary.md）

VS Code で `summary.md` を開きます（右上の「プレビュー」ボタンで表として表示できます）。
**確信度の低いものから順に**並んでいます。上から確認していくと、人の判断が必要なものから見られます。

| 列 | 意味 |
|---|---|
| 承認 | **あなたが記入する列**。AI の推奨案が下書きされています |
| CID | 警告の番号。`G1（3 件）` は、同じ原因の警告をまとめたグループ |
| 推奨 | AI の推奨（修正 / 逸脱） |
| 確信度 | 高：根拠がすべてコード上で確認できた／中：一部に推定を含む／低：コードだけでは判断できない |
| チェッカー・Impact・場所 | 警告の種類、重要度、ファイルと関数 |
| 見立て | 判断の決め手の 1 行要約 |
| グループ | グループの番号 |
| 検証 | 自動検証の結果（成功 / 失敗 / 警告残 / 新規 n 件 / -＝未実施） |
| ずれ | 解析時のコードと今のコードのずれ（なし / あり / 不明） |
| 詳細 | 詳細レポートへのリンク |

**確認のコツ**
- 確信度「高」は、見立てを読んで納得できれば、そのまま承認して構いません。
- 確信度「中」「低」は、詳細レポートを開いて根拠を確認してください。
- 実物の例：[docs/sample-output/summary.md](sample-output/summary.md)

### 3.2 詳細レポート（cid/<CID>.md）

| 章 | 内容 | 読むべきとき |
|---|---|---|
| 1. 結論 | 推奨案、確信度とその理由、見立て、注意点 | 毎回 |
| 2. 警告の概要 | CID、ファイル、関数、行（グループなら全 CID） | 必要に応じて |
| 3. 真偽の根拠 | Coverity の警告経路と、AI が調べた結果・根拠の場所 | 確信度が中・低のとき |
| 4. 案A: 逸脱 | 逸脱する場合の Classification / Action / Severity と逸脱コメント | 逸脱を選ぶとき |
| 5. 案B: 修正 | 修正の内容、影響範囲、差分ファイル（`.patch`）・修正後ファイルの場所 | 修正を選ぶとき |
| 6. 自動検証の結果 | ビルド・再解析の結果 | 検証したとき |
| 7. 処理情報 | 調査・修正の起点のリビジョン、処理時間 | 必要に応じて |

- 修正の中身は、5 章の差分ファイル（`patches/<CID>-fix.patch`）を VS Code で開くと確認できます。
- 実物の例：[docs/sample-output/cid/20002.md](sample-output/cid/20002.md)

## 4. 承認を記入する

### 4.1 一覧サマリの承認列を書く

`summary.md` の「承認」列に、次のいずれかを書きます（推奨案が下書きされているので、変えたい行だけ書き換えます）。

| 書く内容 | 意味 | 反映すると |
|---|---|---|
| `修正` | 修正案を採用する | git：プルリクエストを作成／svn：ワーキングコピーに差分を適用（Coverity には登録しない。修正後の解析で警告が消えるため） |
| `逸脱` | 修正せず、逸脱コメントで済ませる | Coverity に Classification / Action / Severity と逸脱コメントを登録 |
| `却下` | どちらの案も採用しない | 何もしない（次回の実行で再び対象になる。グループの場合は次回から 1 件ずつ調査される） |
| 空欄 | 今回は決めない | 何もしない（あとで記入して反映できる） |

- グループ（`G1（3 件）` など）は 1 行でまとめて承認します。一部だけ扱いを変えたい場合は `却下` にしてください。次回の実行で 1 件ずつ調査されます。
- 表の区切り記号 `|` は消さないでください。

### 4.2 逸脱コメントを手直しする（必要な場合）

詳細レポート（`cid/<CID>.md`）の「4. 案A: 逸脱」の中を直接書き換えます。

```
<!-- ct:begin deviation -->        ← この行は消さない
- Classification: False Positive   ← 値は書き換えてよい
- Action: Ignore
- Severity: Unspecified
- 逸脱コメント:

ここを書き換えてよい（複数行も可）
<!-- ct:end deviation -->          ← この行は消さない
```

- `<!-- ct:begin ... -->` と `<!-- ct:end ... -->` の行（プレビューでは見えない行）は消さないでください。反映時に、この間の内容を読み取って Coverity に登録します。
- 修正案のコードを直したい場合は、承認を `却下` にして手で修正するか、反映後のプルリクエスト上で修正してください。

---

## 5. 承認を反映する

Copilot Chat で次を入力します（実行フォルダは、`summary.md` があるフォルダです）。

```
/coverity-apply <出力先>/<実行日時>
```

1. AI が反映する件数（修正 n 件 / 逸脱 n 件 / 却下 n 件）を表示し、**よいか尋ねます**。内容を確認して「はい」と答えると反映されます。
2. 結果が表示されます。

| | git の場合 | svn の場合 |
|---|---|---|
| 修正 | 修正ブランチを push し、**プルリクエストを作成**（URL が表示されます）。あとは通常どおりレビュー・マージしてください | **ワーキングコピーに差分を適用**します。内容を確認して、**自分でコミット**してください |
| 逸脱 | Coverity に登録 | Coverity に登録 |

- 一部が失敗した場合も、成功した分は反映済みです。原因を直してもう一度 `/coverity-apply` を実行すると、**未反映の分だけ**反映されます（同じ内容が二重に登録されることはありません）。
- 「確認後に一覧サマリまたはレポートが変更されました」と出た場合は、確認の後にファイルが変わっています。もう一度 `/coverity-apply` を実行してください。

---

## 6. 中断した実行を再開する

途中で VS Code を閉じた、エラーで止まった、などの場合は、続きから再開できます。

```
/coverity-resume <出力先>/<実行日時>
```

- 処理済みの警告は飛ばし、途中だったものとエラーになったものをやり直します。

---

## 7. 効果を確認する

```
/coverity-stats
```

これまでの実行について、次を集計して表示します。

- 承認の内訳（修正 / 逸脱 / 却下）
- AI の推奨どおりに採用された割合（全体・確信度別）
- 逸脱コメントが手直しされた割合
- 1 件あたりの処理時間

推奨どおりの採用率が低い、手直しが多いなどの傾向があれば、設定担当者に共有してください。AI への指示（Skill）の改善に使います。

## 8. 困ったとき

| 表示されたメッセージ・症状 | 原因と対処 |
|---|---|
| エージェントの一覧に `coverity-triage` が出ない | プラグインが未インストール。1.2 を確認。インストール直後は VS Code を再起動 |
| `ファイルが見つかりません: ...\.coverity-triage\config.yaml` | 対象リポジトリのフォルダを開いていない、または設定が未作成。`.coverity-triage` があるフォルダを開く。無ければ設定担当者に連絡 |
| `条件ファイルが見つかりません` | ファイル名の誤り。`.coverity-triage/filters/` にあるファイル名を指定 |
| `設定値が不正です` / `YAML の書式が不正です` | 設定ファイルの書き間違い。メッセージに出ている項目を確認し、設定担当者に連絡 |
| `Coverity Connect への接続はまだ実装されていません` | 本番接続の準備中（導入手順書 10 章）。設定担当者に連絡 |
| 認証エラー・接続できない | 1.4 の環境変数が未設定、または設定後に VS Code を再起動していない |
| `環境変数 GITHUB_TOKEN に GitHub のトークンが設定されていません` | 1.4 で `GITHUB_TOKEN` を設定し、VS Code を再起動 |
| `プルリクエストの作成に失敗しました (403)` など | トークンの権限不足、または期限切れ。導入手順書 2 章 No.5 の権限で発行し直す |
| `〇〇 の承認列が不正です` | 承認列に `修正` / `逸脱` / `却下` 以外が書かれている |
| `逸脱の節の目印（ct:begin / ct:end）が見つかりません` | 詳細レポートの目印の行を消してしまった。4.2 の形に戻す |
| `svn patch で競合が発生しました` | 修正を作った後にワーキングコピーの同じ箇所が変わった。表示された差分ファイルを見て手で反映する |
| 一覧サマリに「エラー」の表がある | その警告は処理できなかった（内容が表に書かれています）。原因を直して 6 章の再開を実行すると、エラー分だけやり直されます |
| 一覧サマリに「未処理」がある | 途中で止まった。6 章の再開を実行 |
| レポートに「パスを自動で対応づけました」「対応づけられませんでした」 | Coverity のファイルパスとリポジトリのパスが違う。設定担当者に連絡（導入手順書 4.1 の `path_strip_prefixes`） |
| 処理がとても遅い | 件数を減らした条件で実行する。自動検証（特に再解析）は時間がかかる |

解決しない場合は、実行フォルダの `operations.log`（操作の記録。パスワード等は伏せてあります）を添えて、設定担当者に連絡してください。

## 9. 用語

| 用語 | 意味 |
|---|---|
| CID | Coverity の警告の番号 |
| トリアージ | 警告が本物のバグか誤検知かを判断し、対応（修正 / 逸脱）を決めること |
| 逸脱 | 警告を修正せず、問題がない理由をコメントに残して許容すること |
| 確信度 | AI の判断の確かさ（高 / 中 / 低）。基準は 3.1 を参照 |
| グループ | 同じ原因と判断された複数の CID のまとまり。1 つの案で扱う |
| 実行フォルダ | 1 回の実行の結果が入るフォルダ（`<出力先>/<実行日時>/`） |
| 差分ファイル（.patch） | 修正前後の違いを書いたファイル。VS Code で開くと変更箇所が見られる |
| 自動検証 | 修正案をビルド・再解析して、警告が消えたかを確かめる機能 |
