# 社内の環境での動作確認の手順

社内の PC でプラグインが動くかを確かめる手順です。確かめることのほとんどは `/coverity-selftest` が行い、結果を 1 つのフォルダにまとめます。かかる時間は 1 時間くらいです（④ のビルドを除く）。

VS Code と Copilot CLI の**両方**で行ってください。ただし、取得・統合・検証のサブエージェント、`ct.py tick` に従う進め方、初回解析は、Copilot CLI を対象に作っています。VS Code で動かないところがあれば、そのまま記録してください。

## 1. 必要なもの

[README](../README.md) の「必要なもの」と同じです。③④ には、`/coverity-setup` を済ませた社内のリポジトリが要ります。

## 2. プラグインを入れる

[README](../README.md) の「はじめての準備」の 1 のとおりに入れます。

> 記録：実際にした操作と、うまくいったか（エラーが出たら、その表示をそのまま）

新しい PC では、ここで `/coverity-setup` を最後まで済ませます（uv、サブエージェント 4 つ、再起動）。

## 3. `/coverity-selftest` を実行する

| 範囲 | 確かめること | 開いておくフォルダ |
|---|---|---|
| ① 組み込み | MCP サーバ、`/` メニュー、サブエージェント（作業）の起動・使えるツール・スキルの読み込み・モデル、配置（取得・作業・統合・検証の 4 つの定義）。取得・統合・検証のサブエージェントも起動でき、使えるツールが決めたとおりか（取得：MCP の `search_issues` と `get_issues` があり、ターミナルと `update_triage` が無い。統合・検証：ターミナルと MCP のツールが無い） | どこでもよい |
| ② 偽データでの一連の流れ | 実行（`ct.py tick` に従い、取得と作業のサブエージェントで進める）→ 一覧とレポートの形 → グループ → AI の結論 → 利用者のファイルが変わらないこと → 書き戻しの安全策 → 反映。見本のリポジトリは結果のフォルダの中に作るので、開いているリポジトリには触れません | どこでもよい |
| ③ 社内の Coverity（読み取りだけ） | 準備の状況、接続と認証、検索、警告経路、解析リビジョン、実際の警告 1 件の調査。初回解析（サーバへの登録）はしません | `/coverity-setup` 済みの社内のリポジトリ |
| ④ ビルドでの検証（オプション） | Coverity のコマンド、試しのビルド。初回解析を使う設定なら、サーバへの登録に使う `cov-commit-defects` が見つかるか（登録そのものは試しません） | ③ と同じ（ビルドでの検証か初回解析のため、ビルドのコマンドを設定してあるときだけ） |

1. 社内のリポジトリ（①② だけなら、どのフォルダでもよい）を開き、`/coverity-selftest` を実行する。範囲を絞るときは `/coverity-selftest ①②` のように書く。
2. 途中で、`/` メニューの表示などを 1 つずつ聞かれるので答える。
3. 終わると、結果のフォルダ（既定は `%USERPROFILE%\coverity-triage-selftest\<日時>\`）の場所と、成功・失敗などの件数が出る。

③ でも Coverity には書き込みません（トリアージの書き戻しも、初回解析の登録もしません）。

## 4. 結果を渡す

結果のフォルダには `report.md`（項目ごとの結果）と `raw/`（原因を調べるための記録）があります。フォルダごと渡してください。ホスト名・ユーザ名・認証情報は伏せてあり、社内のソースコードは入っていませんが、ストリーム名やファイルのパスは残るので、確かめてから渡してください。

## 5. 手で確かめること

`/coverity-selftest` では確かめられないことです。

| 確かめること | 方法 |
|---|---|
| 準備の案内 | 新しい PC（または uv を消した状態）で `/coverity-setup` を実行し、uv を入れる → サブエージェントを置く → 設定ファイル → 認証情報（伏せ字の欄） → 再起動 → もう一度 `/coverity-setup` → 接続の確認、まで迷わずに進めるか。かかった時間 |
| 伏せ字の入力 | 認証キーを入れるとき、ターミナルの伏せ字の欄に入れられるか（入れられないときは、渡されたコマンドを自分の PowerShell で実行する流れになるか） |
| ふだんの流れ | 社内のリポジトリで `/coverity-run` → 画面の「結果」で承認 → `/coverity-apply` を一度通す。確認の画面が何回出たか、1 件の確認にかかった時間、気になった点（遅い、読みにくいなど） |
| 画面 | `/coverity-run` を始めるとブラウザに「監視」が開くか。調べている作業がボードに出て、進むにつれて変わるか。終わると「結果」が開き、承認を選ぶと保存されるか。詳細から差分と修正後のファイルを開けるか。タブを閉じても、同じアドレスで開き直せるか。「サーバを止める」で止まるか |
| 夜間の処理 | 件数の多い条件で `/coverity-run` を始めて離れ、朝に終わっているか（止まっていたら、どこで何が出ていたか。画面の「監視」の「重大なエラー」と「⚠ 停止?」の表示も記録する） |
| 初回解析（使うときだけ） | `/coverity-run 最初に解析して` で始め、ビルド → 解析 → サーバへの登録が終わってから警告を取り始めるか。Coverity の画面で、条件ファイルのストリームに新しいスナップショット（版は今のコミット）ができたか。かかった時間。`/coverity-selftest` は登録を試さないので、ここで確かめます |
| 統合と検証（使うときだけ） | 設定でオンにして `/coverity-run` を通し、画面の「監視」に統合と検証の枠が出るか。一覧ができる前は承認を選べず、できたあとは選べるか。詳細レポートに「独立した検証」が出るか |

> 記録：項目ごとの結果（○ / ×）と、エラーの表示（そのまま）

## 6. あわせて教えてほしいこと

- 社内のコーディング規約の資料（スキル `code-fix` に取り込みます）
- 社内の Coverity Connect の Classification / Action / Severity の選択肢（スキル `deviation-comment` の表を社内の値に合わせます）
