# Coverity トリアージエージェント 仕様書（策定中）

## 0. 目的（最優先事項）

これまで人間が実施してきた Coverity 警告のトリアージ作業を代替し、**人間の作業工数を削減する**こと。
以降のすべての仕様判断はこの目的に照らして行う。

## 1. 前提（キックオフで確定）

| 項目 | 内容 |
|---|---|
| エージェント基盤 | GitHub Copilot |
| 準拠仕様 | agent plugin 1.0.0（GitHub Copilot のエージェントプラグイン形式） |
| スクリプト言語 | Python |
| 対象 VCS | git / svn |
| 処理概要 | API でユーザ指定条件にマッチする CID を取得し、警告内容とソースコードを調査してトリアージ結果を出力する |
| 出力の特徴 | 警告内容にかかわらず「ソースコード修正案」と「逸脱コメント（トリアージコメント）案」の**両方**を出力し、人間がどちらを選ぶか判断しやすい情報を添える |
| git での修正出力 | 修正ブランチを作成する |
| 想定構成 | agent.md / SKILL.md / MCP / Python スクリプト等（詳細は相談しながら決定） |

## 2. 決定事項

| No | 項目 | 決定内容 |
|---|---|---|
| D-1 | プラグイン仕様 | GitHub Copilot のエージェントプラグイン形式に準拠する |
| D-2 | 実行形態 | VS Code（エージェントモード）と GitHub Copilot CLI の**両対応** |
| D-3 | Coverity 製品 | Coverity Connect（オンプレ） |
| D-4 | SVN での修正コード出力 | CID ごとに `svn diff` 形式の差分ファイル（`svn patch` で取り込み可能）を出力し、あわせて修正後ファイルをワーキングコピーのディレクトリ構造を保ったまま別領域に出力する |
| D-5 | 対象言語 | C / C++（それ以外の言語は将来対応） |
| D-6 | 対象チェッカー | Coverity 標準チェッカー、MISRA C / C++、CERT C / C++ |
| D-7 | エージェントが案を出す項目 | Classification、Action、Severity、コメント（逸脱理由）。現行の人間のトリアージ項目と同じ |
| D-8 | Coverity への書き戻し | 人間の承認後に書き戻す（承認なしの自動書き戻しはしない） |
| D-9 | 検証環境 | エージェント実行環境でビルドおよび Coverity 再解析（cov-build / cov-analyze）が可能 |
| D-10 | 修正案の自動検証 | オプションとする（実行時に「検証なし / ビルドのみ / ビルド＋再解析」を選択可能） |
| D-11 | 対象 CID の指定方法 | 絞り込み条件で指定する（CID の直接指定・保存済みビュー・自然言語指定は採用しない） |
| D-12 | 絞り込み条件の項目 | プロジェクト / ストリーム、チェッカー名、Impact、トリアージ状態（Classification / Action / Status） |
| D-13 | 絞り込み条件の入力方法 | 条件ファイル（YAML など）で指定し、必要に応じてチャットで条件を追加・上書きできる |
| D-14 | 1 回の処理件数 | 場合による（少数の日常運用と大量の一括処理の両方を想定） |
| D-15 | 大量処理への対応 | 1 回の実行の上限件数を設定可能とし、進捗をファイルに記録して中断・再開（処理済み CID のスキップ）に対応する |
| D-16 | 解析リビジョンとの整合 | 原則として Coverity が解析したリビジョンのコードで調査する。それができない場合は手元のコードを使い、解析時とのずれを検出してレポートに明記する |
| D-17 | 解析リビジョンの特定方法 | 次の優先順で使う。(1) スナップショットに記録されたリビジョンを自動取得する（記録する項目は設定で変更可能）(2) 記録が無ければ条件ファイル等でユーザが指定したリビジョンを使う (3) どちらも無ければ手元のコードを使い、ずれを検出して報告する（D-16）。なお現状はスナップショットにリビジョンを記録していないが、記録する運用に変更可能 |
| D-18 | レポート形式 | Markdown。CID ごとの詳細レポートと、全体の一覧サマリを出力する |
| D-19 | 承認と書き戻しの方法 | 人間がレポート（Markdown）の承認欄に「修正 / 逸脱 / 却下」を記入し（内容の手直しも可）、書き戻しを指示すると承認済みの CID だけ Coverity に登録する |
| D-20 | CID ごとのレポートの内容 | 必須：修正案、逸脱コメント案、Classification / Action / Severity 案。判断材料：真偽の見立てと根拠（警告経路の追跡結果）、推奨案と確信度（高 / 中 / 低）、修正の影響範囲とリスク、自動検証の結果（実施した場合） |
| D-21 | 逸脱コメントの書式 | 社内の既存書式は無いため、本仕様で定める（D-22〜D-24） |
| D-22 | 逸脱コメントの言語 | 日本語 |
| D-23 | 逸脱コメントの要素 | 必須：判定区分（誤検知 / 意図的 など）、理由。追加：コード上の根拠箇所（ファイル・関数・行）、影響がないことの説明 |
| D-24 | 逸脱コメントの体裁 | 見出しを付けない文章形式（例：「誤検知。get_buf() の戻り値は NULL になり得るが、呼び出し元 read_all()（src/io/reader.c:120）で NULL を除外してから渡しているため、当該経路で NULL 参照は発生せず動作・安全性への影響はない。」） |
| D-25 | git の修正ブランチの単位 | 設定で選択する。(a) CID ごとに 1 ブランチ (b) 実行ごとに 1 ブランチ（CID ごとに 1 コミット）。(b) の場合、ブランチは承認の反映時に、承認された修正だけを集めて作る（design 8.3 I-2） |
| D-26 | git での差分ファイル出力 | ブランチに加えて、SVN と同じく CID ごとの差分ファイル（.patch）も出力する |
| D-27 | git の承認後の処理 | レポートで「修正」が承認された分について、修正ブランチをリモートに push し、プルリクエストを作成する（承認前は push しない） |
| D-28 | git サーバ | GitHub / GitHub Enterprise |
| D-29 | SVN の承認後の処理 | 「修正」が承認された差分を `svn patch` でワーキングコピーに適用するまで行う（コミットは人間が行う） |
| D-30 | 「修正」承認時の Coverity 書き戻し | 書き戻さない（修正後の解析で警告が消えるため） |
| D-31 | 「逸脱」承認時の Coverity 書き戻し | 提案（または人間が手直し）した Classification / Action / Severity と逸脱コメントを登録する |
| D-32 | 「却下」時の扱い | 何もしない。Coverity への書き戻し・修正の適用は行わず、条件に合えば次回の実行で再度トリアージ対象になる |
| D-33 | Coverity から取得する情報 | 基本情報（CID、チェッカー、ファイル、関数、Impact、現在のトリアージ属性）に加え、イベント（警告経路）、チェッカーの説明・CWE。トリアージ履歴・類似 CID の過去トリアージは取得しない |
| D-34 | 認証情報の保管場所 | 環境変数から読み込む（Coverity・GitHub とも。認証方式は U-2 で保留中） |
| D-35 | 実行 OS | Windows |
| D-36 | 対象ソースの文字コード | UTF-8 と Shift_JIS（CP932）が混在し得る。修正時はファイルごとに元の文字コード・改行コードを保持して保存する |
| D-37 | 修正案の制約 | 最小限の修正（リファクタリング・整形はしない）、関数の外部仕様（引数・戻り値・公開ヘッダ等）を変えない、既存のコードスタイルに合わせる、社内コーディング規約に従う |
| D-38 | 制約内で修正できない場合 | 制約を超えた修正案を作成し、どの制約を超えたかと影響範囲をレポートに明記する（「必ず両方の案を出す」前提を維持） |
| D-39 | 複数 CID の処理制御 | `/coverity-run` の Skill に従うメインの AI（親）が CID 一覧と進捗を管理し、CID ごと（グループ化した場合はグループごと、D-53）に新しいサブエージェント（独立したコンテキスト）で調査する。VS Code・CLI の両方で同じ仕組みとする |
| D-40 | Coverity API の提供形態 | Python 製の MCP サーバとして、CID 検索・イベント取得・トリアージ書き戻し等をツールで公開する（REST / SOAP の違いは MCP サーバ内で吸収する） |
| D-41 | VCS 操作の提供形態 | MCP サーバのツールとして提供する（解析リビジョンの取り出し、ブランチ作成、差分ファイル・別領域出力、push・プルリクエスト作成、svn patch 適用）。git / SVN の違いはツール内で吸収する |
| D-42 | 自動検証のコマンド指定 | ビルドコマンドおよび cov-build / cov-analyze の引数を設定ファイルに記述し、MCP ツールがその設定どおりに実行する（エージェントが任意のコマンドを組み立てない） |
| D-43 | 出力先 | 設定で指定したフォルダの下に、実行ごとのサブフォルダ（例：`<出力先>/20261002-153000/`）を作り、レポート・差分ファイル・別領域出力・進捗ファイルを出力する |
| D-44 | 効果測定の記録 | 採用状況の集計（修正 / 逸脱 / 却下の件数、推奨案どおりに採用された割合）、人間の手直しの記録（承認時に書き換えられた逸脱コメント・属性の差分）、CID ごとの処理時間を記録する |
| D-45 | Python 外部パッケージ | pip で自由にインストール可能 |
| D-46 | Python バージョン | 3.12 以上（ユーザ回答「自由に選べる」を受け、MCP SDK の要件と保守期間を考慮して設定） |
| D-47 | 使用する AI モデル | 調査を行うサブエージェント（`coverity-triage-worker`）はエージェント定義で gpt-6 luna に固定する（変更するときは `.agent.md` の `model:` を書き換える。設定ファイルには持たない）。入口の Skill（準備・実行の進行・反映・質問）は、利用者がチャットで選んでいるモデルで動く（Skill はモデルを指定できないため。D-80） |
| D-48 | 推奨案（修正 / 逸脱）の決定方針 | エージェントの判断に任せる（真偽の見立て・修正リスク・影響範囲を総合）。ユーザが方針を指定したい場合は、プロジェクトの知識のファイルの「推奨の方針」に書く（D-78。当初「将来設ける」としていたカスタムプロンプトの .md を、このファイルで実現） |
| D-49 | 設定ファイルの分割 | プロジェクト設定（Coverity サーバ URL、出力先、ブランチ単位、検証コマンド、リビジョンの記録項目、上限件数など）と、絞り込み条件（実行ごとに使い分け、複数用意可能）を別ファイルにする |
| D-50 | 設定ファイルの置き場所 | 対象リポジトリ内（例：`<ワーキングコピー>/.coverity-triage/`）に置き、コミットしてチームで共有する。絞り込み条件ファイルも同じ場所に置ける。認証情報は環境変数（D-34）のため含めない |
| D-51 | CID 処理中のエラー | その CID をスキップして続行する。エラー内容を進捗ファイルとレポートに記録し、再開時にエラー分だけやり直せるようにする |
| D-52 | 同一原因の複数 CID | グループ化してまとめて 1 つの修正案・逸脱コメント案を提示し、まとめて承認できるようにする |
| D-53 | グループ化の方法 | MCP ツールが規則（同じチェッカーかつ同じマクロ / 同じ関数 / 同じ行 など）で機械的に候補を作り、グループ単位でサブエージェントが調査する。調査の結果、原因が異なる CID はグループから外して個別処理に戻す。これにより D-39 の処理単位は「CID またはグループ」となる |
| D-54 | 一覧サマリの並び順 | 確信度の低い順（人間の判断が必要なものから確認できるようにする） |
| D-55 | 一覧サマリの列 | 必須：CID、推奨案、確信度、承認欄、CID ごとの詳細レポートへのリンク。追加：チェッカー名・Impact、ファイル・関数、真偽の見立て（1 行要約）、グループ ID・自動検証の結果・解析時とのリビジョンのずれの有無 |
| D-56 | 承認の記入場所 | 一覧サマリの承認列のみ。逸脱コメントや属性の手直しは CID ごとのレポートで行う（D-19 を具体化） |
| D-57 | 作業領域 | 利用者のワーキングコピーには触れず、別の作業領域を作る。実現方法は、エクスポートしたスナップショット（`git archive` / `svn export`）に作業項目ごとの変更を重ねる方式とし、git のコミット・ブランチは一時インデックスで作る（当初案の worktree / checkout から変更、design 8.3 I-1）。例外は SVN の承認後適用（D-29） |
| D-58 | 調査と修正の起点リビジョン | 真偽の調査は解析リビジョンで行い、修正案（git ブランチ・差分ファイル・別領域出力）は取り込み先の最新リビジョン（設定で指定したブランチの先頭）を起点に作る。最新リビジョンで既に解消済みの場合はその旨を報告する |
| D-59 | 逸脱コメントの記録先 | 設定で選択する。(a) Coverity Connect のトリアージコメントのみ（D-31）(b) あわせてソースコードへのアノテーション（例：`/* coverity[<イベントのタグ>:FALSE] 理由 */`。誤検知は `:FALSE` を付け、意図的は付けない）を追加する差分も「逸脱案」として出力する |
| D-60 | アノテーション方式での「逸脱」承認時 | アノテーションの差分を修正と同じ流れで反映する（git：ブランチ＋push＋プルリクエスト（D-27）、SVN：ワーキングコピーへの適用（D-29））。あわせて Coverity に属性とコメントを書き戻す（D-31） |
| D-61 | 利用者向けの操作 | 次の 5 つを用意する。(1) 初期設定：設定ファイル・条件ファイルのひな形を対象リポジトリに生成 (2) トリアージ実行 (3) 再開：実行フォルダを指定して続きから再開（エラー分のやり直しを含む）(4) 承認の反映：一覧サマリの承認列に従い Coverity 書き戻し・push・プルリクエスト作成・svn patch 適用 (5) 効果測定の集計：D-44 の記録を複数回の実行にまたがって集計 |
| D-62 | 承認列の初期値 | 全件に推奨案を下書きしておく。人間は確認して残すか書き換える |
| D-63 | 反映前の確認 | 「承認の反映」の開始時に、反映する件数（修正 n 件 / 逸脱 n 件 / 却下 n 件）を表示し、人間の同意を得てから実行する |
| D-64 | 確信度の基準 | 明文化した基準を Skill に記載する。初期基準 — 高：警告経路をコード上で最後まで追え、根拠がすべてコードにある（自動検証を実施した場合はそれが成功）。中：根拠の一部に推定を含む。低：実行時の値や外部仕様など、コードから判断できない前提に依存する |
| D-65 | 使い方の資料 | 人が読む資料はリポジトリ直下の README だけにし、5 分以内で理解できる分量にする。設定項目の説明・困ったときの対処などの詳細は AI が読む資料（Skill）に移し、利用者は AI に質問する。導入手順書・利用手順書（docs/setup-guide.md、docs/user-guide.md）は廃止する |
| D-66 | セットアップの進め方 | `/coverity-setup` で、AI と対話しながら進める。対象リポジトリにチーム共通の設定が無ければ、最初に使う人が対話で作ってコミットする（導入担当者と利用者を区別しない）。設定があれば個人の PC の準備だけを行う。何度実行してもよく、不足分だけを補う |
| D-67 | セットアップで AI が行う作業 | プラグインに必要なもの一式（uv のインストール、Python とライブラリの準備、環境変数の設定、設定ファイルの作成、接続テスト）。git / svn / Coverity / VS Code 自体には触れない。ターミナルでの実行は、毎回利用者の確認を得てから行う |
| D-68 | 認証情報の入力 | AI がスクリプトを実行し、ターミナルに伏せ字の入力欄を出して利用者が入力する。値は環境変数に保存し、チャットや AI には渡さない |
| D-69 | 利用者向けの入口 | `/coverity-setup`（準備と設定）、`/coverity-run`（実行。未完了の実行があれば再開を提案）、`/coverity-apply`（承認の反映。実行フォルダ省略時は最新）、`/coverity-help`（使い方・エラーの意味・設定変更・効果測定を AI に聞ける）の 4 つ。D-61 の 5 つの操作は機能として維持する |
| D-70 | セットアップで決める設定値 | 利用者に聞くのは Coverity の URL・プロジェクト・ストリームの 3 つだけ（接続できたら一覧から選ぶ）。git / svn、取り込み先ブランチ、文字コード、パスの対応づけ、出力先、条件ファイル（未トリアージ・上限 20 件）は自動で決めて一覧で確認を求める。その他は既定値とし、必要なら `/coverity-help` で変更する |
| D-71 | 対象プロジェクトのビルド方法 | `make -f makefileXX` によるクロスコンパイル。ビルド前に環境設定のスクリプト（例 `envset.bat`）を、2 つの引数を渡して実行する。引数の意味はエージェントでは扱わず、設定（`setup_command`）に書かれた値をそのまま渡す（`{root}` だけはビルド用にコピーしたフォルダに置き換える。引数はいくつでも書ける）。フルビルド＋Coverity 解析は 10〜60 分 |
| D-72 | 自動検証のまとめ方 | 検証（ビルドのみ / ビルド＋再解析）は、作業項目ごとではなく、**全件の調査が終わった後に 1 回だけ**行う。その実行の修正案をすべて適用したコードで 1 回ビルド（＋解析）し、再解析の場合は修正前のコードの解析（1 回）と比べる。これにより 1 回の実行での解析は 2 回分で済む（D-10 の実現方法を変更） |
| D-73 | まとめた検証の結果の割り当て | CID ごとに警告が消えたかを判定する。ビルドエラーや新しい警告は、そのファイル・関数を変更した修正案に割り当て「要確認」とする（修正案同士の影響は区別しきれないことを明記） |
| D-74 | 検証で問題が出た場合の確信度 | ビルド失敗・警告が残った・新しい警告が出た修正案は、確信度を自動で「低」に下げ、理由に検証の問題を付記する。推奨案は変えない（D-64 を補足） |
| D-75 | 検証の設定 | 設定に `verify.setup_command`（ビルド前に同じコマンドプロンプトで実行。`{root}` は検証用にコピーしたフォルダに置き換える）を追加する。`/coverity-setup` の最後に任意で「自動検証も設定しますか」と聞き、使う場合は環境設定とビルドのコマンドを聞いて、修正前のコードで試しにビルドが通ることを確かめる。後から `/coverity-help` でも設定できる（D-70 を補足） |
| D-76 | ビルドするディレクトリ | `cov-build`（ビルド）は、`envset` の後に、makefile があるリポジトリ内の決まった 1 か所のディレクトリへ移動してから実行する。設定に `verify.build_dir`（リポジトリからの相対パス）を追加し、ツールはビルド用コピー内のそのディレクトリへ**絶対パスで**移動する（`envset` が現在のディレクトリを変えても影響を受けない。Windows では `cd /d` でドライブもまたぐ）。`--dir`（中間ディレクトリ）の相対パスは、移動先が基準になる |
| D-77 | Coverity Connect の API の使い分け | 公開されている実装例・スキーマで要求と応答の形を確認できたものだけを使う。**REST API v2**：警告の検索（`POST /api/v2/issues/search`）とトリアージの書き戻し（`PUT /api/v2/issues/triage`、Coverity Connect 2022.6.0 以降）。**SOAP API v9**：警告経路（`getStreamDefects`）とスナップショットの情報（`getSnapshotsForStream` / `getSnapshotInformation`）。REST の警告経路（`GET /api/v2/issues/sourceCodeInfo`、2023.9.0 以降）は形が公開されていないため、調査スクリプトで応答を記録し、使えると分かれば切り替えを検討する（U-1 を決定） |
| D-78 | 人の判断を次回に活かす | 対象リポジトリに**プロジェクトの知識のファイル**（`.coverity-triage/knowledge.md`、コミットしてチームで共有）を置く。内容は「調査で使う事実」「推奨の方針（修正か逸脱か）」「逸脱コメントの書き方」を 1 項目 1 行で書く。作業項目の調査の前に AI が読む（知識とコードが食い違う場合はコードを優先し、レポートに書く）。承認の反映の後、人が推奨案を変えた・逸脱コメントを手直しした・却下した作業項目から、AI が一般化した知識の候補を下書きして示し、**人が選んだもの（直したもの）だけ**を追記する。D-48 の「方針を書く .md」はこのファイルの「推奨の方針」で実現する |
| D-79 | 1 回の実行で対象にするストリーム | 1 つだけ（条件ファイルの `streams` に 2 つ以上書くとエラー）。複数のストリームをまとめて扱うのは今後の拡張とする |
| D-80 | 入口の作り方 | D-69 の 4 つは、利用者だけが呼べる **Skill**（`disable-model-invocation: true`）として作る。エージェントが読む調査用の Skill は利用者の `/` メニューに出さない（`user-invocable: false`）。カスタムエージェントは調査用のサブエージェント `coverity-triage-worker` だけとし、使えるツールを調査用に限定する。反映の安全策は、ツール側の確認（`preview_apply` の件数提示と確認用の文字列が無いと `apply_approvals` は反映しない、D-63）で担保する。理由：VS Code ではプロンプトファイル形式のコマンドが新しい実行方式で非推奨となり Skill への移行が案内されていること、Copilot CLI ではプロンプトファイルが対象外であること、Agent Plugins 1.0 で VS Code・CLI 共通の部品は Skill と MCP であること（2026-10-04 に公式ドキュメントで確認） |
