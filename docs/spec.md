# Coverity トリアージエージェント 仕様書（策定中）

## 0. 目的（最優先事項）

これまで人間が実施してきた Coverity 警告のトリアージ作業を代替し、**人間の作業工数を削減する**こと。
以降のすべての仕様判断はこの目的に照らして行う。

## 1. 前提（キックオフで確定）

| 項目 | 内容 |
|---|---|
| エージェント基盤 | GitHub Copilot |
| 準拠仕様 | agent plugin 1.0.0（GitHub Copilot のエージェントプラグイン形式） |
| スクリプト言語 | Python |
| 対象 VCS | git / svn |
| 処理概要 | API でユーザ指定条件にマッチする CID を取得し、警告内容とソースコードを調査してトリアージ結果を出力する |
| 出力の特徴 | 警告内容にかかわらず「ソースコード修正案」と「逸脱コメント（トリアージコメント）案」の**両方**を出力し、人間がどちらを選ぶか判断しやすい情報を添える |
| git での修正出力 | 修正ブランチを作成する |
| 想定構成 | agent.md / SKILL.md / MCP / Python スクリプト等（詳細は相談しながら決定） |

## 2. 決定事項

| No | 項目 | 決定内容 |
|---|---|---|
| D-1 | プラグイン仕様 | GitHub Copilot のエージェントプラグイン形式に準拠する |
| D-2 | 実行形態 | VS Code（エージェントモード）と GitHub Copilot CLI の**両対応** |
| D-3 | Coverity 製品 | Coverity Connect（オンプレ） |
| D-4 | SVN での修正コード出力 | CID ごとに `svn diff` 形式の差分ファイル（`svn patch` で取り込み可能）を出力し、あわせて修正後ファイルをワーキングコピーのディレクトリ構造を保ったまま別領域に出力する |
| D-5 | 対象言語 | C / C++（それ以外の言語は将来対応） |
| D-6 | 対象チェッカー | Coverity 標準チェッカー、MISRA C / C++、CERT C / C++ |
| D-7 | エージェントが案を出す項目 | Classification、Action、Severity、コメント（逸脱理由）。現行の人間のトリアージ項目と同じ |
| D-8 | Coverity への書き戻し | 人間の承認後に書き戻す（承認なしの自動書き戻しはしない） |
| D-9 | 検証環境 | エージェント実行環境でビルドおよび Coverity 再解析（cov-build / cov-analyze）が可能 |
| D-10 | 修正案の自動検証 | オプションとする（実行時に「検証なし / ビルドのみ / ビルド＋再解析」を選択可能） |
| D-11 | 対象 CID の指定方法 | 絞り込み条件で指定する（CID の直接指定・保存済みビュー・自然言語指定は採用しない） |
| D-12 | 絞り込み条件の項目 | プロジェクト / ストリーム、チェッカー名、Impact、トリアージ状態（Classification / Action / Status） |
| D-13 | 絞り込み条件の入力方法 | 条件ファイル（YAML など）で指定し、必要に応じてチャットで条件を追加・上書きできる |
| D-14 | 1 回の処理件数 | 場合による（少数の日常運用と大量の一括処理の両方を想定） |
| D-15 | 大量処理への対応 | 1 回の実行の上限件数を設定可能とし、進捗をファイルに記録して中断・再開（処理済み CID のスキップ）に対応する |
| D-16 | 解析リビジョンとの整合 | 原則として Coverity が解析したリビジョンのコードで調査する。それができない場合は手元のコードを使い、解析時とのずれを検出してレポートに明記する |
| D-17 | 解析リビジョンの特定方法 | 次の優先順で使う。(1) スナップショットに記録されたリビジョンを自動取得する（記録する項目は設定で変更可能）(2) 記録が無ければ条件ファイル等でユーザが指定したリビジョンを使う (3) どちらも無ければ手元のコードを使い、ずれを検出して報告する（D-16）。なお現状はスナップショットにリビジョンを記録していないが、記録する運用に変更可能 |
| D-18 | レポート形式 | Markdown。CID ごとの詳細レポートと、全体の一覧サマリを出力する |
| D-19 | 承認と書き戻しの方法 | 人間がレポート（Markdown）の承認欄に「修正 / 逸脱 / 却下」を記入し（内容の手直しも可）、書き戻しを指示すると承認済みの CID だけ Coverity に登録する |
| D-20 | CID ごとのレポートの内容 | 必須：修正案、逸脱コメント案、Classification / Action / Severity 案。判断材料：真偽の見立てと根拠（警告経路の追跡結果）、推奨案と確信度（高 / 中 / 低）、修正の影響範囲とリスク、自動検証の結果（実施した場合） |
| D-21 | 逸脱コメントの書式 | 社内の既存書式は無いため、本仕様で定める（D-22〜D-24） |
| D-22 | 逸脱コメントの言語 | 日本語 |
| D-23 | 逸脱コメントの要素 | 必須：判定区分（誤検知 / 意図的 など）、理由。追加：コード上の根拠箇所（ファイル・関数・行）、影響がないことの説明 |
| D-24 | 逸脱コメントの体裁 | 見出しを付けない文章形式（例：「誤検知。get_buf() の戻り値は NULL になり得るが、呼び出し元 read_all()（src/io/reader.c:120）で NULL を除外してから渡しているため、当該経路で NULL 参照は発生せず動作・安全性への影響はない。」） |
| D-25 | git の修正ブランチの単位 | 設定で選択する。(a) CID ごとに 1 ブランチ (b) 実行ごとに 1 ブランチ（CID ごとに 1 コミット） |
| D-26 | git での差分ファイル出力 | ブランチに加えて、SVN と同じく CID ごとの差分ファイル（.patch）も出力する |
| D-27 | git の承認後の処理 | レポートで「修正」が承認された分について、修正ブランチをリモートに push し、プルリクエストを作成する（承認前は push しない） |
| D-28 | git サーバ | GitHub / GitHub Enterprise |
| D-29 | SVN の承認後の処理 | 「修正」が承認された差分を `svn patch` でワーキングコピーに適用するまで行う（コミットは人間が行う） |
| D-30 | 「修正」承認時の Coverity 書き戻し | 書き戻さない（修正後の解析で警告が消えるため） |
| D-31 | 「逸脱」承認時の Coverity 書き戻し | 提案（または人間が手直し）した Classification / Action / Severity と逸脱コメントを登録する |
| D-32 | 「却下」時の扱い | 何もしない。Coverity への書き戻し・修正の適用は行わず、条件に合えば次回の実行で再度トリアージ対象になる |
| D-33 | Coverity から取得する情報 | 基本情報（CID、チェッカー、ファイル、関数、Impact、現在のトリアージ属性）に加え、イベント（警告経路）、チェッカーの説明・CWE。トリアージ履歴・類似 CID の過去トリアージは取得しない |
| D-34 | 認証情報の保管場所 | 環境変数から読み込む（Coverity・GitHub とも。認証方式は U-2 で保留中） |
| D-35 | 実行 OS | Windows |
| D-36 | 対象ソースの文字コード | UTF-8 と Shift_JIS（CP932）が混在し得る。修正時はファイルごとに元の文字コード・改行コードを保持して保存する |
| D-37 | 修正案の制約 | 最小限の修正（リファクタリング・整形はしない）、関数の外部仕様（引数・戻り値・公開ヘッダ等）を変えない、既存のコードスタイルに合わせる、社内コーディング規約に従う |
| D-38 | 制約内で修正できない場合 | 制約を超えた修正案を作成し、どの制約を超えたかと影響範囲をレポートに明記する（「必ず両方の案を出す」前提を維持） |
| D-39 | 複数 CID の処理制御 | 親エージェントが CID 一覧と進捗を管理し、CID ごと（グループ化した場合はグループごと、D-53）に新しいサブエージェント（独立したコンテキスト）で調査する。VS Code・CLI の両方で同じ仕組みとする |
| D-40 | Coverity API の提供形態 | Python 製の MCP サーバとして、CID 検索・イベント取得・トリアージ書き戻し等をツールで公開する（REST / SOAP の違いは MCP サーバ内で吸収する） |
| D-41 | VCS 操作の提供形態 | MCP サーバのツールとして提供する（解析リビジョンの取り出し、ブランチ作成、差分ファイル・別領域出力、push・プルリクエスト作成、svn patch 適用）。git / SVN の違いはツール内で吸収する |
| D-42 | 自動検証のコマンド指定 | ビルドコマンドおよび cov-build / cov-analyze の引数を設定ファイルに記述し、MCP ツールがその設定どおりに実行する（エージェントが任意のコマンドを組み立てない） |
| D-43 | 出力先 | 設定で指定したフォルダの下に、実行ごとのサブフォルダ（例：`<出力先>/20261002-153000/`）を作り、レポート・差分ファイル・別領域出力・進捗ファイルを出力する |
| D-44 | 効果測定の記録 | 採用状況の集計（修正 / 逸脱 / 却下の件数、推奨案どおりに採用された割合）、人間の手直しの記録（承認時に書き換えられた逸脱コメント・属性の差分）、CID ごとの処理時間を記録する |
| D-45 | Python 外部パッケージ | pip で自由にインストール可能 |
| D-46 | Python バージョン | 3.12 以上（ユーザ回答「自由に選べる」を受け、MCP SDK の要件と保守期間を考慮して設定） |
| D-47 | 使用する AI モデル | エージェント定義で固定する。デフォルトは親エージェント・サブエージェントとも gpt-6 luna。後から変更できるようにする |
| D-48 | 推奨案（修正 / 逸脱）の決定方針 | 当面はエージェントの判断に任せる（真偽の見立て・修正リスク・影響範囲を総合）。将来は、ユーザがカスタマイズできるカスタムプロンプトの .md を 1 つ設け、そこで方針を指定できるようにする |
| D-49 | 設定ファイルの分割 | プロジェクト設定（Coverity サーバ URL、出力先、ブランチ単位、検証コマンド、リビジョンの記録項目、上限件数など）と、絞り込み条件（実行ごとに使い分け、複数用意可能）を別ファイルにする |
| D-50 | 設定ファイルの置き場所 | 対象リポジトリ内（例：`<ワーキングコピー>/.coverity-triage/`）に置き、コミットしてチームで共有する。絞り込み条件ファイルも同じ場所に置ける。認証情報は環境変数（D-34）のため含めない |
| D-51 | CID 処理中のエラー | その CID をスキップして続行する。エラー内容を進捗ファイルとレポートに記録し、再開時にエラー分だけやり直せるようにする |
| D-52 | 同一原因の複数 CID | グループ化してまとめて 1 つの修正案・逸脱コメント案を提示し、まとめて承認できるようにする |
| D-53 | グループ化の方法 | MCP ツールが規則（同じチェッカーかつ同じマクロ / 同じ関数 / 同じ行 など）で機械的に候補を作り、グループ単位でサブエージェントが調査する。調査の結果、原因が異なる CID はグループから外して個別処理に戻す。これにより D-39 の処理単位は「CID またはグループ」となる |
| D-54 | 一覧サマリの並び順 | 確信度の低い順（人間の判断が必要なものから確認できるようにする） |
| D-55 | 一覧サマリの列 | 必須：CID、推奨案、確信度、承認欄、CID ごとの詳細レポートへのリンク。追加：チェッカー名・Impact、ファイル・関数、真偽の見立て（1 行要約）、グループ ID・自動検証の結果・解析時とのリビジョンのずれの有無 |
| D-56 | 承認の記入場所 | 一覧サマリの承認列のみ。逸脱コメントや属性の手直しは CID ごとのレポートで行う（D-19 を具体化） |
| D-57 | 作業領域 | 利用者のワーキングコピーには触れず、別の作業領域を作る（git は worktree、SVN は別ディレクトリへの checkout）。例外は SVN の承認後適用（D-29） |
| D-58 | 調査と修正の起点リビジョン | 真偽の調査は解析リビジョンで行い、修正案（git ブランチ・差分ファイル・別領域出力）は取り込み先の最新リビジョン（設定で指定したブランチの先頭）を起点に作る。最新リビジョンで既に解消済みの場合はその旨を報告する |
| D-59 | 逸脱コメントの記録先 | 設定で選択する。(a) Coverity Connect のトリアージコメントのみ（D-31）(b) あわせてソースコードへのアノテーション（例：`// coverity[<checker>] 理由`）を追加する差分も「逸脱案」として出力する |

## 3. 未決定事項

| No | 項目 | 保留理由 | 確認先・次のアクション |
|---|---|---|---|
| U-1 | 使用する API（REST API v2 / SOAP Web Services API / 併用） | SOAP でしか取得できない情報があるとの情報があり、要確認 | 取得する情報は D-33 で確定。D-33 の各情報（特にイベント＝警告経路）と、D-31 の書き戻し（トリアージ属性・コメントの更新）が、社内サーバのバージョンの REST v2 / SOAP のどちらで可能かを確認して決定する |
| U-2 | 認証方式 | 社内 Coverity サーバの仕様を確認しないと判断できない | 社内 Coverity サーバの仕様（バージョン、認証方式）を確認する |
| U-3 | 社内コーディング規約の内容 | 規約の資料が未共有 | ユーザから規約資料を共有してもらい、修正用の Skill に取り込む |
